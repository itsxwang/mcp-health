Method & environment

How the MCP Health Index smoke-tests servers — and exactly what the isolation does and does not guarantee.

What a "run" is

  1. Install — npm package → fresh npm install --prefix $TMP; PyPI → fresh uv venv $TMP/venv + uv pip install. Never installed globally.
  2. Handshake — act as an MCP client over stdio (official mcp SDK): protocol initialize.
  3. List tools / resources — capability discovery, with latency.
  4. One harmless call — a tool whose name matches read-only verbs (list/get/read/search/…), called with inert arguments built only from required schema fields (enum→first value, default, or "test"/1/0). Names matching destructive verbs are skipped. Returned content is truncated.

Isolation that exists

  • Resource limits on the server process: 60 CPU-s, 2 GiB address space, 64 child processes, 64 MiB file writes, 256 fds, no core dumps.
  • Fresh sanitized environment: no inherited tokens/secrets, throwaway HOME/TMPDIR, all installs ephemeral in a temp dir that is deleted.
  • Hard wall clock: SIGALRM + parent SIGKILL to the entire process group (each candidate runs in its own session).
  • Network namespace isolation: bubblewrap --unshare-net

What isolation does NOT protect against

  • Network egress (current run): server code could exfiltrate data or scan the network. Mitigated by the sanitized empty environment (nothing to steal) but not prevented.
  • Sandbox is not a security boundary against a truly malicious package — a determined attacker inside the resource limits can still make outbound network calls. Treat every server as hostile.
  • Tool calls are heuristic: name-based read-only detection can mislabel a tool. Inputs are inert, but a read-only call can still hit an external API with our placeholder credentials.
  • We do not audit the code; "PASS" means "booted, listed tools, answered one read-only call".
