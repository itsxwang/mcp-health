Methodology

Credibility is the product. This page is the full, honest description of what a test is, what it proves, what it does not prove, and where the sandbox stops.

What a run is — exactly

  1. Ephemeral install — npm: fresh npm install --prefix $TMP; PyPI: fresh uv venv $TMP/venv + uv pip install. Nothing is ever installed globally; the temp directory is deleted after the run. Install (network allowed) is a separate step from run.
  2. Handshake — we act as an MCP client over stdio with the official mcp SDK and complete the protocol initialize. Latency is recorded.
  3. Capability discovery — tools/list and resources/list, with latency and tool count.
  4. One harmless call — we pick a tool whose name matches read-only verbs (list/get/read/search/describe/…) and never matches destructive verbs (delete/create/send/exec/…). Arguments are built only from the tool's required schema fields, with inert values (enum's first value, the declared default, or a literal like "test"/1/false; path-like fields get the empty throwaway working directory). Returned content is truncated. If no tool passes the name filter, the call is skipped and the server is PARTIAL — we never fire a blind call.

What PASS means

The package, installed from its declared registry on the test date, spoke MCP over stdio well enough to: boot under our resource limits, complete the initialize handshake, list its tools, and answer one read-only call without an error result.

What PASS does not prove

  • Not a security audit. We do not read or review server code. "PASS" means it boots and responds — nothing about the code's intent or quality.
  • Not protocol correctness. One round-trip is not a conformance suite.
  • Not a guarantee for your configuration. Servers with required API keys are tested with an inert placeholder (mcp-health-index-placeholder) — many credential-dependent servers therefore show FAIL/PARTIAL by design.
  • Not permanent. Results are stamped with the test date. Anything older than 7 days is marked stale on the site until the daily run refreshes it.

Isolation that exists

  • Resource limits on every server process: 60 CPU-seconds, 2 GiB address space, 2048-task cap (fork-bomb protection), 64 MiB file writes, 1024 fds, no core dumps.
  • A sanitized environment: no inherited tokens or secrets, throwaway HOME/TMPDIR, ephemeral installs in a temp dir that is deleted.
  • Hard wall clock: every candidate runs in its own OS session/process group; a SIGALRM watchdog and the orchestrator both end with SIGKILL to the entire group — a hung or fork-bombing server cannot outlive its budget.
  • Network namespace isolation: OFF for the 228 recorded results (stale capability probe, now fixed). New runs put server processes inside a bubblewrap network namespace when the host allows (verified working here).

What isolation does NOT protect against

  • Network egress. Mitigations that reduce (not eliminate) exposure: the environment contains no secrets and nothing valuable is on disk. See the README SAFETY section for the full story.
  • The sandbox is not a security boundary. rlimits bound resources, not capabilities. A truly malicious package inside those limits can still make outbound network calls. That is why runs happen on throwaway machines (CI runners), not workstations.
  • Tool-call selection is heuristic. Name-based read-only detection can mislabel a tool; inputs are inert, but a read-only call can still trigger an external API call with our placeholder credentials.

FAQ

Is this affiliated with Anthropic or the MCP project?

No. The MCP Health Index is an independent, community project. It uses the public MCP registry API and the open-source mcp SDK. Not affiliated with Anthropic, and not part of the Model Context Protocol project.

How do you test without running malicious code?

We do run third-party code — on purpose, inside an isolation layer (ephemeral installs, resource limits, no secrets, hard kill, own process group) on a throwaway machine. See the "Isolation that exists" and "does NOT protect against" sections above, plus the SAFETY section in the repo's README. There is no perfect sandbox here; the honest answer is "limits + throwaway environment", not "safety".

Why did my server fail?

Every server's page shows the exact captured error and the server's stderr tail from the run — see the index link from the announcement or search the table. The most common causes: (1) the package requires API keys at boot, (2) the package is a CLI tool rather than a stdio MCP server (prints usage and exits), (3) declared bin/entrypoint doesn't resolve, (4) it needs services (databases, daemons, browsers) we don't provide.

How do I get a re-test?

Open the submission form with your package name — open issues are ingested by the daily cron and re-queued automatically. For urgent re-tests, email xion.dev7@gmail.com.
